# M10.4 AppleA7IOPNub publication check

## Result: BLOCKED — no evidence supports a Device Tree property correction

The M10.3 claim that the DCP `AppleARMIODevice` provider had no
`gIODTPlane` children was incorrect.  The Stage-A guest probe was repeated
after repairing the host executor's completion sentinel.  It reached
`bash-5.3#`, ran the signed `openios-ioreg` utility, and returned exit status
zero.

The live registry states that the same `AppleARMIODevice` object that
provides `AppleASCWrapV6` also has the original DT nub as a child:

```text
dcp: class=AppleARMIODevice
  IODeviceTree child: iop-dcp-nub (class=IOService)
iop-dcp-nub:
  compatible=iop-nub,rtbuddy-v2|
  parent in IODeviceTree: dcp (class=AppleARMIODevice)
AppleASCWrapV6: published beneath that dcp provider
AppleA7IOPNub: not published
RTBuddy: not published
```

The probe retained exactly the original DCP-nub properties.  In particular,
both the original and probe DT contain `name=iop-dcp-nub`,
`compatible=iop-nub,rtbuddy-v2`, `AAPL,phandle`, `continuous-time`,
`quiesced`, `coredump-*`, `no-firmware-service`, `user-power-managed`, and
`watchdog-enable`; neither contains `device_type`, `reg`, or `role` on that
child.  Adding those fields would therefore not reproduce the hardware DT and
would be speculative.

## Static boundary

The 23G71 Boot KC path still establishes that `AppleA7IOP::start` calls its
child-nub routine after its initialization branch.  The routine obtains a
child iterator in `gIODTPlane`, and its `AppleA7IOPNub::withRegistryEntry`
path calls `nub->init(child, gIODTPlane)`.

Disassembly of `AppleA7IOPNub::init` at `0xfffffff0080d87b0` shows a
delegated superclass/virtual initializer and its boolean return handling; it
does not directly read or compare `device_type`, `reg`, or `role`.  This does
not prove the delegated initializer succeeds, nor that the child-nub loop is
reached in the live kernel.  A published `AppleASCWrapV6` service alone is not
proof that its `start()` completed.

```sh
  --dtree /tmp/test-dcp.dtree \

```

Observed result: prompt in 23.89 seconds; command exit status 0; no
`AppleA7IOPNub` or `RTBuddy` service in the utility's `IOService` traversal.

## Executor repair and regression

`guest_exec.py` had used `%%d` in its `printf` format.  That made the guest
print a literal `%d` and could cause the parser to treat an unparsable result
as zero.  It now uses `%d`.  The repaired transport was checked against the
unchanged M1 assets with both `echo OPENIOS_GUEST_EXEC_SENTINEL_OK` (zero) and
`false` (correctly reported non-zero).

No QEMU source, Device Tree input, original M1 APFS, or original trustcache
was modified in M10.4.

## Next concrete action

The earliest remaining unknown is runtime control flow: whether
`AppleA7IOP::start` reaches its child-nub loop, and if it does, which
`withRegistryEntry`/delegated-initializer check rejects the candidate.  The
smallest defensible next action is log-only, source-matched kernel lifecycle
instrumentation in a separately signed experimental Boot KC.  That requires a
verified experimental Boot-KC build/sign/boot workflow, which is not present
in this Ubuntu workspace.  No QEMU MMIO, RTKit, DART, firmware, or DT behavior
is justified before that observation exists.
