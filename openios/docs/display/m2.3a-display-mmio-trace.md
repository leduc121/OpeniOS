# M2.3a T8120 display MMIO trace

## Result

The iOS 26.6 restore-ramdisk boot reached `bash-5.3#` with tracing enabled,
both with the diagnostic graphics console disabled and enabled. Neither boot
made an observed unassigned access to any of the 19 selected T8120 display
MMIO ranges: both summaries reported zero reads and zero writes.

This is evidence about the current restore-ramdisk boot only. It is not proof
that a full iOS userspace never accesses these blocks, nor that all possible
display registers are covered. The M2.2 test pattern remains an
emulator-generated diagnostic image; no displayed pixel has been attributed
to the guest.

## Instrumentation

The Darwin machine has a new `display-mmio-trace` boolean property. It is off
by default. When enabled, it activates a filtered observer in QEMU's existing
`unassigned_mem_read()` and `unassigned_mem_write()` paths in
`system/memory.c`. No MemoryRegion, fake device, interrupt, DMA path, or
register response was added.

The observer covers 19 physical ranges from the D74AP inventory for
`dart-disp0`, `dart-dcp`, `disp0`, `dart-dispgrt`, `dcp`, `scaler0`, and
`gfx-asc`. Each matching record includes direction, physical address, access
size, value (write data, or the value returned by the existing unassigned read
path), range name, and `result=unassigned`. Per-range and total counters are
printed on exit. Detailed records are capped at 256 while counters continue,
so logging is bounded without losing aggregate access counts.

An unassigned read already returned zero before this change. The tracer merely
reports that dispatch result; it does not make a zero-returning shim equivalent
to passive observation.

The current Darwin implementation maps RAM and its existing CPU, AIC, AMCC,
SEP, and UART-related regions, but does not instantiate a T8120 display, DCP,
GPU, or display DART device. Consequently, an access to one of the selected
unmapped display addresses reaches the observed unassigned dispatch path.

Enable it by adding the property to the existing machine arguments:

```sh
-machine darwin,display-mmio-trace=on
```

It can be combined independently with `test-display=on`.

## Build and preservation

QEMU-SPTM 11.1.0 is pinned at
`bad6336fb24211f8c4e8e946c259bd5b12417340`. The parent repository preserves
this work as the second patch in `openios/patches/qemu-sptm/series`:

```sh
openios/tools/qemu/apply-sptm-patches.sh
```

The application script checks the pinned revision, validates the complete
series in a temporary tree before modifying QEMU, supports an already-applied
series, and never resets or cleans local QEMU work. Applying both patches to a
detached clean worktree passed, as did a second idempotency run.

The tested build command was:

```sh
cd third_party/darwin-vm/qemu-sptm/build
../configure --target-list=aarch64-softmmu --disable-pvg --disable-werror
ninja -j2 qemu-system-aarch64
```

`--disable-werror` remains necessary with GCC 15 because baseline
`apple_aic.c` emits an existing enum-pointer `sscanf` format warning. This
work neither suppresses that warning in source nor changes AIC code. The build
passed using at most two jobs.

## Tests and captured accesses

| Test | Result | Display MMIO summary |
| --- | --- | --- |
| Trace off, `test-display=off`, full M1 boot | Reached `bash-5.3#` | Tracer inactive, as intended |
| Trace on, `test-display=off`, full M1 boot | Reached `bash-5.3#`; `uname`, `id`, and `ls` succeeded | 0 reads, 0 writes |
| Trace on, `test-display=on`, full M1 boot | Reached `bash-5.3#`; serial console remained functional | 0 reads, 0 writes |
| Trace on, paused CPU, monitor `xp /1wx 0x230000000` | Operational control produced one record | 1 read in `disp0.0` |

The operational-control record was:

```text
openios-display-mmio: #1 read addr=0x230000000 size=4 value=0x0 range=disp0.0 result=unassigned
```

That access was generated deliberately from the QEMU monitor, not by iOS. It
demonstrates that the zero-access guest results are distinct from a tracer that
was not running. Both guest runs emitted the tracer's enable message and a
complete 19-range zero summary on controlled exit.

The tests used the existing firmware, device tree, SPTM, TXM, restore ramdisk,
and trustcache listed in `qemu-test-console-prototype.md`; none was downloaded
or modified.

## Interpretation and limitations

Within the selected ranges and the interval from reset through the restore
shell prompt, the guest did not issue an access that reached QEMU's unassigned
memory callbacks. The minimal restore environment likely does not match or
start the full display/DCP/GPU driver stack. A fuller boot environment with the
relevant Apple display services and firmware would be needed to determine the
normal initialization sequence.

The observer intentionally sees only unassigned dispatches. A future mapping
over one of these addresses would need tracing at that MemoryRegion or a more
general memory-dispatch tracepoint. The inventory may also be incomplete, and
the experiment does not reveal driver matching failures, power-domain state,
or accesses performed outside the selected ranges. It emulates no DCP
firmware, GPU, DART, DisplayPipe registers, or framebuffer DMA.

## Recommendation for M2.3b

First establish whether the relevant display, DCP, GPU, and DART services and
kexts are published and matched in a fuller iOS boot environment. Correlate
that lifecycle with a broader, still bounded physical-memory trace, then add
tracepoints to any real mapped regions if necessary. Only after guest-originated
accesses are observed should work proceed toward register semantics or a
guest-driven framebuffer path; do not infer T8120 behavior from the T8030
Inferno DisplayPipe implementation alone.
