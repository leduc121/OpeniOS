# M10.5 AppleA7IOP lifecycle trace

## Result: PARTIAL — the earliest observed blocker is the IOMMU-mapper wait before child nubs

M10.5 used the original M1 Boot KC, SPTM, TXM, ramdisk, trustcache, and boot
arguments.  It generated a disposable DCP-only Device Tree from the original
tree, restoring only the previously tested DCP compatibility group.  Neither
the original DT nor any firmware asset was changed.

Both controls reached `bash-5.3#` and ran their marker with exit status zero:

| DT | Marker | Prompt | Result |
| --- | --- | --- | --- |
| normal fixed-up | `OPENIOS_M105_BASELINE_TRACE` | 21.45 s | PASS |
| DCP-only | `OPENIOS_M105_DCP_TRACE` | 21.61 s | PASS |
| DCP-only, CPU trace | `OPENIOS_M105_BRANCH_TRACE` | 21.64 s | PASS |

The M1 APFS and trustcache were read only for these runs.

## QEMU gdbstub lifecycle evidence

Ubuntu's installed `gdb-multiarch` 17.1 accepts the AArch64 target. QEMU was
started paused with `-S` and a per-run Unix-domain gdbstub socket under `/tmp`.
The socket was local-only and removed after every run. All breakpoints below
were GDB hardware breakpoints, so no Boot KC byte or firmware asset changed.

The boot KC SHA-256 was
`39b8c25fc62be20999d9f12dfc1562ddb1036742b11cffce76e42d2c9677226c`.
The first breakpoint verifies the slide and bytes:

```text
Breakpoint at 0xfffffff0280d6314
pc  = 0xfffffff0280d6314
x0  = 0x0
x30 = 0xfffffff0280d6314
=> cmp x0, #0x0
   cset w8, ne
   strb w8, [x20, #354]
   ldr x0, [x20, #248]
   bl  0xfffffff02a507f68
   mov x17, x24                 # 0xfffffff0280d6328
```

Hardware breakpoints at the direct-call return site `0xfffffff0280d6328` and
the following decision `0xfffffff0280d6364` did not fire during a 14-second
bounded interval. After GDB detached, the same DCP-only guest reached
`bash-5.3#` in the following eight seconds. Therefore the calling kernel
thread does not return through `0x...0d6328` in this boot, while the system as
a whole continues; the boundary is before `createChildNubs`.

Static decoding of the direct helper shows a lookup of `iommu-parent`; the
immediately preceding Boot KC string is `waitForSystemMapper`. The stripped
release KC cannot prove its exact C++ symbol, so this report calls it the
**mapper-wait helper**. The DT establishes the dependency:

```text
original DCP: iommu-parent = 0xad
original mapper-dcp: AAPL,phandle = 0xad, compatible = iommu-mapper
DCP-only probe: iommu-parent = 0xad, mapper-dcp compatible removed
```

Thus the evidence-backed conclusion is that the published ASC thread waits at
the mapper dependency before child-nub construction. This is not evidence that
`AppleA7IOPNub::init`, attach, or `registerService` failed.

A disposable DCP-plus-DART-compatible control also did not reach the return
site within 14 seconds and did not reach a shell in the next eight seconds.
This matches the earlier bounded DART negative result but is not proof of a
deadlock and does not justify DART register emulation.

## Non-invasive execution evidence

QEMU's built-in `-d in_asm,cpu` and `-dfilter` were used with the observed
23G71 Kernel Collection slide (`+0x20000000`).  With the normal fixed-up DT,
the trace contained only common code at `0xfffffff0280d8274`, `0x...82a0`,
`0x...8840`, and `0x...886c`.  With the DCP-only DT it additionally executed
the static `AppleA7IOP` code slice at:

```text
0xfffffff0280d7db8
0xfffffff0280d7f94
0xfffffff0280d7fa0
0xfffffff0280d6314
```

At `0xfffffff0280d6314`, the register trace recorded an `AppleA7IOP`-like
object in `x20` and entered the direct helper call at
`0xfffffff02a507f68`, with return address `x30=0xfffffff0280d6328`.  This is
runtime evidence that the DCP-only path reaches this post-virtual-call portion
of the disassembled start sequence. The gdbstub result above further shows the
call does not return through `0xfffffff0280d6328` during the bounded boot.

The exact instructions of interest in the unslid 23G71 Boot KC are:

```text
...0d6360  blraa x9, x17       # virtual call
...0d6364  tbz   w0, #0, ...   # skip child-nub routine if bit 0 is clear
...0d6370  bl    ...0d6430     # candidate createChildNubs entry
...0d6430                       # child iterator entry
...0d87b0                       # AppleA7IOPNub::init entry (static mapping)
```

None of `0x...0d6364`, `0x...0d6370`, `0x...0d6430`, or `0x...0d87b0` was
observed by the bounded QEMU TB trace. Hardware breakpoints now strengthen the
result for `0x...0d6328` and `0x...0d6364`; the latter path remains unexecuted
in the DCP-only boot. It would be incorrect to call this an initializer
failure.

## Instruction-level and Boot-KC feasibility

The build has QEMU's plugin API and `contrib/plugins/libexeclog.so`, which can
register per-instruction callbacks.  Its address filters are a sound next
mechanism in a persistent local session, but the sandboxed background process
used for this investigation is reaped when its launcher exits; it did not
yield a durable guest trace.  No result from that attempted callback run is
used as lifecycle evidence.

The host's native `/usr/bin/gdb` has no AArch64 target, but installed
`/usr/bin/gdb-multiarch` does; it produced the hardware-breakpoint results
above.

An experimental Boot KC is also not reproducible on this Ubuntu host:

- `kmutil` is absent;
- no source-matched iOS 23G71 kernel-development image or KDK is present;
- the local QEMU-SPTM guide's KC process requires macOS, an exact KDK,
  `kernel.development.*`, extension manifest, and `kmutil create`;
- `ldid`/trustcache handle the proven userspace Mach-O workflow only.  They do
  not authenticate or construct an iOS Boot KC.

Therefore M10.5 made no QEMU, Device Tree, firmware, MMIO, DART, RTKit, or
mailbox behavior change.  A QEMU-side lifecycle logger would be an opt-in
diagnostic change, but it cannot be justified as a hardware correction and is
not needed to preserve the baseline.

## Exact commands and raw outputs

Create the disposable DT:

```sh
python3 openios/tools/display/make_display_probe_dtree.py \
  openios/firmware/linux/iphone15-3-26.6/boot/dtree.original \
  /tmp/openios-m105-dcp.dtree --nvram third_party/darwin-vm/nvram.bin \
  --disable-network --enable dcp
```

The trace runs used the historical QEMU options plus:

```text
-d in_asm,cpu
-dfilter 0xfffffff0280d6300+0x100,0xfffffff02a507f00+0x200
-D /tmp/openios-m105-dcp-branch.log
```

Raw transient artifacts are `/tmp/openios-m105-{baseline,dcp}-inasm.log`,
`/tmp/openios-m105-dcp-branch.log`, and their matching `*-serial.log` files.
They are deliberately outside Git because they contain boot output and are
reproducible from the commands above.

## Smallest next action

### M10.6 mapper resolution refinement

A second local GDB session stopped at verified runtime addresses.  It showed
that the virtual `getProperty("iommu-parent")` return at
`0xfffffff02a507fdc` is non-null.  The subsequent registry-resolution call at
`0xfffffff02a5081e8` also returns a non-null object at
`0xfffffff02a5081ec`.  Thus phandle `0xad` and the `mapper-dcp` registry entry
are available even when its `iommu-mapper` compatible is suppressed.

The next direct call is `0xfffffff02a4bf3b4`, with the resolved object in
`x0`, `x1 = -1`, and `x2 = 0`; the caller expects its return at
`0xfffffff02a508200`.  Its exact stripped symbol is not established, but the
unbounded timeout-shaped argument and the nearby `waitForSystemMapper` string
make this the current candidate wait boundary.  This is stronger than the old
claim that the mapper is absent, which is now retracted.  It does not prove
which IOMMU service/class must publish, nor a DART register failure.

The narrow DCP + `mapper-dcp`-compatible control reached `bash-5.3#` in
25.22 seconds and executed `echo M106_MAPPER_ONLY_SHELL` with status 0.  It
shows the mapper compatible alone does not regress M1.  The DCP +
`dart,t8110` controller control was then run as a durable 55-second one-shot
QEMU process with serial redirected directly to
`/tmp/openios-m107-dart-serial.log`. QEMU produced zero serial bytes before
the deliberate timeout sent SIGTERM. This is the first reproducible divergence
from mapper-only, but is a bounded negative result, not proof of deadlock or a
specific DART register failure.

Do not add DT properties or emulate DCP/RTKit.  The next independently
verifiable task is to stop at `0xfffffff02a508200` (the candidate wait return)
while using the narrow DART controller control, then identify the required
AppleT8110DART service publication.  Only a concrete DART initialization
failure can justify an opt-in T8120 DART implementation.
